# Sensor health and asset enrollment limitations (v0.10)

Sentinel tracks only sensors enumerated in `SENTINEL_SENSOR_KEYS`. The authenticated operator endpoint `GET /api/v1/sensors` shows `never_seen` until a configured sensor submits a correctly signed event or heartbeat; `healthy` for server-observed contact within the last 180 seconds; otherwise `stale`. The 180-second window is a demonstrative local default (not a guaranteed availability SLA). All timestamps are generated on the API server. `GET /api/v1/health` only checks the API process; it is **not** proof that sensors are connected.

Run `backend/sentinel/collectors/linux_ssh.py ... --follow` to emit an initial heartbeat and subsequent signed heartbeats every 60 seconds (option `--heartbeat-seconds` between 30 and 120). Without `--follow` it sends one heartbeat before exiting, and will therefore become stale. Heartbeats never trigger malware/network/login alerts and contain only the permitted asset identifier. The collector still only transmits to literal loopback. Stored counters and the latest asset ID are observations, not endpoint attestation or proof of complete coverage. The API audit chain records each accepted heartbeat.

**Trust limitations:** possession of a sensor signing key permits an attacker to forge health and security events. A sensor may stay alive while its log source is incomplete, inaccessible, delayed, or tampered with; therefore a green contact status does not guarantee collection completeness. A sensor cannot change its bound asset after first accepted contact. Optional `SENTINEL_SENSOR_ASSETS` mapping binds **every** configured sensor to a predetermined asset and rejects incorrect events and heartbeats (HTTP 403) before they update state. Without a mapping, the first signed contact pins an asset (trust on first use), which is **not** approved enrollment. Re-enrollment requires a reviewed offline recovery procedure and sensor key rotation; there is no remote rebind endpoint. Stolen signing keys can still forge contact and telemetry for the bound asset. Stale calculation uses the server clock, and requires a running API. A valid signed event also counts as healthy contact. The signal is neither a continuous agent attestation nor network IPS.

**Release checks:** signed heartbeat/replay and schema validation; privilege protection on coverage API; stale/never-seen transitions; audit-integrity checks; collector destination restrictions; PostgreSQL CI persistence. Do not enable automated containment based only on this health status.
